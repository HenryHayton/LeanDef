## Object

`VTask.ModEq p a b` is the relation that asserts `a` and `b` are **congruent modulo `p`** in an additive commutative monoid `M`. Concretely, `a ≡ b [PMOD p]` holds when there exist natural numbers `m` and `n` such that adding `m` copies of `p` to `a` gives the same element as adding `n` copies of `p` to `b`. Intuitively, `a` and `b` lie in the same "coset" of the cyclic submonoid generated by `p`.

In the richer setting of an additive commutative **group**, this is equivalent to the more familiar condition that `b − a` is an integer multiple of `p` (i.e., `b − a = m • p` for some `m : ℤ`). Over the natural numbers or integers, it specialises to the usual integer/natural-number modular-congruence relations.

`VTask.ModEq : {M : Type u_1} -> [AddCommMonoid M] -> (p a b : M) -> Prop`

The implicit type argument `M` is the ambient additive commutative monoid in which all elements live. The typeclass instance supplies the monoid structure. The first explicit argument `p` is the **modulus** — the element whose multiples define the equivalence classes. The second argument `a` and the third argument `b` are the two elements whose congruence is being asserted; the notation `a ≡ b [PMOD p]` reads "`a` is congruent to `b` modulo `p`".

## Conventions

The definition is stated for additive commutative monoids, which have no subtraction, so the witness uses two separate natural-number multipliers rather than a single integer multiplier; in a group the two formulations coincide. There are no junk-value conventions declared for this definition.

## Worked examples

- Claim: `VTask.ModEq 3 1 7` holds in `ℕ`, because `1 + 2·3 = 7 + 0·3`.

- Claim: `VTask.ModEq 5 0 10` holds in `ℕ`, because `0 + 2·5 = 10 + 0·5`.

- Claim: `VTask.ModEq p a a` holds for every element `a` and modulus `p` in any additive commutative monoid (reflexivity: take `m = n = 0`).

- Claim: If `VTask.ModEq p a b` and `VTask.ModEq p b c` then `VTask.ModEq p a c` (transitivity, established by `ModEq.trans`).

- Claim: `VTask.ModEq 3 7 1` holds in `ℕ` (symmetry: take `m = 0, n = 2`, giving `0·3 + 7 = 2·3 + 1`).

## Boundaries

- **Modulus `p = 0`**: Every element `m • 0 + a = a`, so the relation `VTask.ModEq 0 a b` reduces to `a = b`.
- **Trivial monoid / `p` very large**: If no nonzero multiples of `p` are reachable, the relation still holds whenever the two bare elements coincide (`m = n = 0`).
- **General additive commutative monoid vs. group**: In a monoid without subtraction, the definition uses two natural-number witnesses and is genuinely asymmetric in its proof term; in an abelian group the condition collapses to the existence of a single integer `m` with `b − a = m • p`, and the two characterisations are provably equivalent.
- **Non-positive moduli in ordered settings**: The definition makes sense for any element `p : M` without positivity hypotheses; positivity conditions appear only in theorems about intervals (`toIcoMod`, `toIocMod`).

## Not to be confused with

- **`Nat.ModEq n a b`** (`a ≡ b [MOD n]`): the standard natural-number congruence defined via `a % n = b % n`; they coincide on `ℕ` but are defined differently.
- **`Int.ModEq n a b`** (`a ≡ b [ZMOD n]`): the integer congruence defined via `n ∣ b − a`; they coincide on `ℤ` but live in a different namespace.
- **`AddSubgroup.quotient` membership**: the abstract coset membership in an additive subgroup, which is more general but less computational than `VTask.ModEq`.
